# Spike S-01 — Muse Code integration (RW-01, High)

Date: 2 Nov 2026 · Binary: Muse Code 1.4.14 (1.4.14-R7309.1) at `~/.local/bin/muse`
Resolves: TRD Q1 / A1 · TASKS S-01 · effort_plan RW-01

## What was tried (exact commands)

```sh
muse --version; muse --help
muse exec --help; muse serve --help; muse schema --help
muse resume --help; muse export --help; muse trace --help
HOME=/tmp/rw-home muse schema generate-ts --out /tmp/rw-schema   # wrote msp.d.ts (4029 lines)
HOME=/tmp/rw-home muse exec --provider echo "Reply with exactly: hello-ripple"        # in /tmp/rw-spike2
HOME=/tmp/rw-home muse exec --provider echo --json "hello json test"
HOME=/tmp/rw-home muse export --last --out /tmp/rw-export.json
muse usage   # -> "not logged in"
```

Sandbox note: under the default shell sandbox, `muse exec` fails with
`failed to acquire the session writer lease … Operation not permitted` because
`~/.config/muse` and the session store are outside the writable roots.
Re-running with `HOME=/tmp/rw-home` (and matching XDG vars) succeeds. RippleWitness
must therefore launch `muse` with a writable HOME/session store, or run outside
that sandbox profile. This is an environment finding, not a Muse defect.

## Observed behaviour

1. **Headless works (echo provider, no credentials).** Plain exec prints
   `echo: Reply with exactly: hello-ripple`, exit 0. With `--json` it emits
   NDJSON records: `schema_version:1`, `payload_type` values include
   `runtime.command.accepted`, `turn.input.user`, `run.output.delta`
   (carries assistant `text`), `run.terminal.completed` (carries final `text`),
   plus `task.lifecycle.*` and a `run.usage` record. This is **not** the
   `AgentEvent = message|tool_call|approval_request|done` shape assumed in
   TRD §5.1 — the adapter must map these payload types.
2. **MSP is real and versioned.** `muse serve` serves the Muse Session
   Protocol over stdio (or `--listen` socket daemon). `muse schema generate-ts`
   exports the authoritative `msp.d.ts`. Method enum (`MspMethod`) includes:
   `session/start`, `session/resume`, `session/fork`, `session/read`,
   `session/list`, `turn/start`, `turn/steer`, `turn/interrupt`,
   `approval/decide`, `approval/listPending`, `session/setApprovalMode`,
   `usage/read`, `model/list`. An official TS SDK repo exists
   (`meta-models/muse-code-sdk`, `@muse-code/sdk` per secondary sources);
   installing it was **not** verified here (no scaffold yet; `npm view`
   hit a sandbox cache EPERM). Do not code against guessed SDK method names —
   code against `msp.d.ts` / the exec JSONL, both observed.
3. **Transcript capture works.** Sessions persist as
   `$XDG_DATA_HOME/muse/sessions/YYYY/MM/DD/<session-id>/session.jsonl`.
   `muse export --last --out <file>` produced a 156 KB JSON document
   (`export_schema_version:1`, messages, tool calls, approvals, model ids).
   This satisfies FR-09's capture need without scraping the TUI.
4. **Resume exists.** `muse resume [--last|<uuid|name>]`. Programmatic
   equivalent is MSP `session/resume`. Interactive picker behaviour was not
   exercised (needs a TTY).
5. **Read-only is expressible, not yet behaviourally proven.** Both
   `muse exec` and the `muse serve` host accept `--disable-write` and
   `--disable-shell`; exec adds `--approval-mode untrusted|on-request|never`.
   On `serve`, sandbox posture is fixed for the host lifetime; approval mode
   is selected on the wire (`session/setApprovalMode`). With the echo
   provider no tool calls occur, so enforcement against a real tool-using
   (meta provider) session remains **unproven** until S-02 credentials exist.
   Per AGENTS Part C, Q&A must therefore *also* run in a throwaway worktree
   copy until that test passes (SEC-07).
6. **Meta provider not tested.** `muse usage` → `not logged in`;
   `META_API_KEY` is unset in this environment. No live session, no credits
   movement, no rate-limit data. See S-02.

## Decision: SDK path vs Plan B

**Adopt a two-step path, both behind TRD §5.1 `AgentSessionPort`:**

- **Step 1 (build now, proven today): `muse exec --json` adapter.**
  PR generation and cross-exam Q&A spawn `muse exec --provider meta --json
  --disable-write --disable-shell --approval-mode untrusted` (Q&A) in a
  throwaway worktree copy; transcript = the session `session.jsonl` /
  `muse export` JSON. Label Q&A `reinstantiated_from_transcript` whenever a
  *new* exec session is seeded with a saved transcript (honesty rule,
  AGENTS Part C §6). This is the documented Plan B, upgraded: exec JSONL is
  a stable observed contract, not screen-scraping.
- **Step 2 (only if time after P0): `muse serve` MSP adapter** implementing
  `session/start` + `turn/start` + `session/resume` from the exported
  `msp.d.ts`, giving true live-session resume. Do not block D-01 on this.

`approvalPolicy: 'read-only'` maps to: exec flags above (or, on serve,
host `--disable-write --disable-shell` + `session/setApprovalMode`).
Anything else in TRD §5.1 stays **[VERIFY]** until a meta-provider session
runs.
